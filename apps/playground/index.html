What is this?

Most ASCII filters map brightness to a character ramp like .:-=+*#%@. That works, but it throws away shape: a diagonal edge and a flat gray patch of the same brightness get the same character.

ASCII FX matches shape. Each cell is compared against the actual pixel shapes of the font's glyphs, and the glyph that reconstructs the cell best wins. Color is fitted per cell on top. Two rules shaped the design:

  • Deterministic. Same input, same characters, everywhere. GPU and CPU agree byte for byte.
  • No startup analysis. A compiler measures the font once and ships a small binary profile.

The pipeline

Once per font, a compiler builds a profile: an 8×8 mask, a coverage value, and an atlas tile per glyph. Then every frame runs four stages. Here is a real frame going through the real code. Hover any stage to follow one cell all the way; drag the columns slider and watch the grid, the samples, and every decision recompute.

Stage 3 colors each cell by its class: gray cells are transparent, blue are flat, orange carry structure worth matching. The sections below take the stages one at a time.

Compile the font

System rasterizers (browser canvas, CoreText, FreeType) all anti-alias differently, and determinism dies there. So the compiler brings its own: integer scanline rasterization into a 64 px cell, 4×4 subsamples per pixel, fixed Bézier flattening, nonzero winding. Same font bytes, same profile bytes, always.

Per glyph it stores:

  • an 8×8 binary mask, 1 = ink. The shape the matcher sees.
  • a 16-bit coverage value: how much of the cell is ink. Drives flat cells.
  • an anti-aliased tile in a texture atlas. Only used for drawing.

Below: the live atlas of whatever font is selected up top. Hover a glyph to see the 8×8 mask the matcher compares against. Notice how thin glyphs like _ and - get sparse or empty masks; those are reached through coverage, not shape.

What can go in a charset? Any code point the font has outlines for. The built-in ascii-blocks set adds half-blocks and quadrants (▀ ▄ ▌ ▚ ▓), and braille patterns (⠏ ⣠ ⣿) are a classic trick: each glyph is a 2×4 dot grid, which hands the matcher 256 distinct shapes. The compiler refuses characters the font lacks, so a compiled profile never contains tofu. Runtime profiles cannot check that; a missing glyph quietly profiles the fallback box. Color emoji are out on three counts: most emoji fonts are bitmap-only with no outlines to rasterize, emoji advance two cells wide so the monospace check fails, and the pipeline fits one ink color per cell, which would repaint them anyway.

The profile records SHA-256 hashes of the font, charset, and parameters. Frames reference profiles by fingerprint, so a frame can never decode against the wrong font.

The grid

Cells are not square, so the cell aspect enters the row count. For source W×H and cell cw×ch:

columns = C            rows = max(1, rdiv(H · C · cw, W · ch))
rdiv(n, d) = floor((2n + d) / 2d)          round half up, used everywhere

The pipeline explorer above prints this exact formula with live numbers as you drag its slider.

Shrink the source

Each cell gets exactly 8×8 = 64 samples: an alpha-weighted box filter over the pixels under each sample.

sample = (rdiv(Σ r·a, Σ a), rdiv(Σ g·a, Σ a), rdiv(Σ b·a, Σ a), rdiv(Σ a, n))

GPU texture filtering is banned here: bilinear taps round differently per vendor. The compute shader does the same integer sums, one workgroup per cell, one lane per sample.

Classify each cell

luma = (77·r + 150·g + 29·b + 128) >> 8
  • Transparent. Mean alpha below 128 (with alpha: mask): blank glyph, done.
  • Flat. Brightest minus darkest luma under the flat slider: no structure worth matching. Pick the glyph whose coverage is closest to the cell's mean luma. Drag to see the whole ramp of this font:
    In full mode both colors are free, so any glyph reconstructs a flat cell. The blank glyph is pinned for stability.
  • Structured. Everything else, below.

The source mask

The darkest and brightest samples become two color endpoints. Each sample joins the nearer one by squared RGB distance. That is a color comparison, not luma: a red stroke on equally bright green still masks cleanly.

Try it. Paint an 8×8 cell below and the real matcher runs on every stroke: endpoint classification, polarity, the Hamming shortlist over the whole charset, and the exact rerank from the next two sections. The preloaded stroke is a soft-edged diagonal. Its gray edge samples join whichever endpoint is nearer, which is why anti-aliased strokes still mask cleanly.

Polarity: glyph masks say 1 = ink, so which source side counts as ink follows from the palette. White on black means the bright side is ink, and the mask is inverted before comparing. This is derived, never a flag. A free invert option would let the shortlist and the rerank optimize different orientations.

Shortlist by shape

d(g) = popcount(maskLo XOR gLo) + popcount(maskHi XOR gHi)

Keep the 8 smallest, ties to the lower glyph id. Hamming is two XORs and two popcounts. The exact error below costs about 64 multiplies per glyph, so: cheap filter over the whole charset, exact score over 8. Same winner, a fraction of the cost. In full mode the score is min(d, 64−d), because free colors can flip orientation.

Fit colors, pick the winner

Partition the cell's 64 samples by the candidate's own mask, then fit:

glyph mask ──▶  ink samples        fg = their mean      (full, foreground)
                the rest           bg = their mean      (full)  or fixed backdrop
mono: both colors fixed by the palette

The mean is the unique minimizer of squared error for a fixed partition, so every candidate is scored with the best colors it could possibly have: 

err(g) = Σ over 64 samples:   c = (bit k of g) ? fg : bg
                              (r − c.r)² + (g − c.g)² + (b − c.b)²

Worst case is 64 · 3 · 255² = 12,484,800, so the comparison fits in exact u32 math. Means are rounded to u8 before scoring, so backends cannot drift. Lowest error wins, ties keep shortlist order. The winner's id and colors are the frame.

Draw it

Each cell samples its glyph's atlas tile and blends fg over bg by coverage. The atlas is mipmapped so strokes keep their weight at any scale. The CPU backend builds the same mip chain in Canvas2D.

Pointer effects (reveal, push, wave, magnify, glyph rotation) warp this composite. They never re-run matching. The GPU evaluates them per pixel, the CPU per cell, same formulas.

Bit for bit on GPU and CPU

  • Integer arithmetic only, one rounding rule. No floats to disagree over.
  • Per-cell sums are u32 atomics. Integer addition is associative, so thread order cannot matter.
  • Every comparison has a written tie-break, implemented identically on both backends.
  • The conformance suite compares raw output arrays across backends, not screenshots.

Going faster

  • Temporal. A cell whose 64 samples did not change re-uses its result. Exact, not approximate.
  • Dirty rectangles. Invalidate a region, re-match only that.
  • Adaptive resolution. Columns drop when the frame rate sags, recover when it is smooth.

Cheaper matchers

  • shape6: a cell as 6 numbers (mean, vertical, horizontal, diagonal, center vs ring, detail), nearest glyph in that space, optional 262,144-entry LUT for O(1) lookups.
  • ramp: coverage only, the classic brightness ramp. A cheap effect, not quality.

Both are opt-in, never a silent fallback, and measurably worse than exact. The repo benchmarks say how much.
